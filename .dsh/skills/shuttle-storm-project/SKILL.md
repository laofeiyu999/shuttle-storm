# shuttle-storm 项目工作须知

## 1. 当前阶段

- 设计文档 **V1.5 已于 2026-11-05 定稿**（`Docs/羽毛球大作战_游戏开发设计文档_V1.5.docx`），当前进入 **弹道仿真可视化系统阶段**，尚未进入正式游戏开发。
- 本阶段工作顺序（用户 2026-11-05 指定）：① 用户自己建模两个演示人物；② AI 修模型、绑骨骼、做挥拍与移动动作；③ AI 写仿真系统（`sim/`，规格见文档 6.2，含弹道与相机对标飞羽青春）；④ 把 3D 人物接入仿真。不要越过用户的建模步骤先做人物资产。
- 仿真系统的玩法口径只取自 V1.5；文档里标“由 sim 重算”的列（防守方可蓄档、可达性等）由仿真跑出后回填文档，标【AI初值·待调】的数值在仿真中初调。
- 未经用户明确要求，不把讨论内容或仿真代码直接做成正式游戏实现。
- 本 Skill 只是 AI 工作须知，不是设计文档，也不另建一套玩法真源。

## 2. 工作入口与最终权

- 开始本项目工作前，先读取 `Docs/` 下用户当前指定的最新设计文档，再读取与当次任务直接相关的资料。
- 用户刚明确拍板、尚未写入文档时，以用户最新明确决定为准，并在后续文档工作中同步写入。
- 决定写入后，以 `Docs/` 下最新设计文档为玩法最终权；具体规则、数值和待决项都到该文档查找，不在本 Skill 另存副本。
- 若无法确认哪份是最新设计文档，先向用户确认，不按文件名、版本号或修改时间自行猜测。
- 旧文档、代码和竞品资料均不得覆盖用户最新决定或最新设计文档。

## 3. 冲突与未知项

- 发现资料冲突时，先指出冲突及各自来源，不私自选择实现最方便的版本。
- 未确定的内容标为 `TBD` 或“待确认”；需要继续推进而缺少关键决策时，向用户提问。
- 区分用户决定、源码事实、视频观察、玩家经验、助手建议和推测；不得把建议、观察或推测写成已拍板规则。
- 不臆造数值、窗口、曲线或机制。用户要求占位演示时，明确标注占位，不将其冒充正式规则。

## 4. 文档修订方式

- V1.5 的 Markdown 源是 `.ua/v15/v15_full.md`，构建脚本 `.ua/v15/build_docx.py`（以 V1.4 docx 为样式模板）。改文档先改 Markdown 源，再重建 docx，不直接手改 docx。
- 用户的拍板记录在 `.ua/v15/user_directives.md`（R1）与 `.ua/v15/user_directives_R2.md`（U00–U42）；新的拍板继续追加编号，并在文档附录 B 加修订行。
- 改口径时全文同步：术语表、正文、第 16 章配置字段、第 17 章验收、第 18 章初值与待定汇总、附录 B，不让新旧口径并存。

## 5. 废弃资料与第三方参考边界

- `Docs/羽毛球大作战_游戏开发设计文档_V1.4(最终版).docx` 是旧版历史档案；未被最新决定或最新设计文档重新确认的旧规则，不自动继承。
- 新仿真系统的玩法逻辑来自用户最新明确决定和最新设计文档；新 UI、视觉表现和技术接口根据最新设计需求与用户当次要求重新设计。
- `References/` 整体只读，只用于研究；不得直接复制第三方代码，第三方美术资源不作本项目资产。
- 参考视频以本地原画质文件为准（远程入库的是 1080p 转码版）；分析结论在 `.ua/v15/r2/v_*.md`，飞羽源码专题在 `.ua/v15/r2/src_fy.md`。

## 6. 工作与交付纪律

- 先理解用户当次任务，再决定是否需要设计推演、资料核查、仿真或编码；不主动扩大实现范围。
- 提出建议时明确说是建议，不替用户拍板；用户否定或修正后，按最新意见执行。
- 修改设计时更新最新设计文档；修改实现时同步必要测试，并列出仍未对齐的部分。
- 每个工作日收工前更新 README“项目进度”表并写 `handoff/YYYY-MM-DD.md`；开工先读最新一份交接。

## 7. 何时修改本 Skill

仅在以下长期工作约定变化时修改：

- 最新设计文档的目录、指定入口或命名规则变化。
- 项目所处阶段、正式开发等工作入口变化。
- AI 的协作方式或交付纪律变化。
- 通用工程约束变化。
- 旧版文档、`References/` 的使用边界变化。

普通玩法、球种、动作、数值、曲线、按键、窗口、蓄力和后摇调整，只改最新设计文档，不改本 Skill；已有实现需要同步时，再同步实现与测试。
